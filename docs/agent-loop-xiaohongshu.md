# 🤯 拆解 Nova Agent Loop（一）：核心循环凭什么只有一个扩展点？

> 这是 Nova 架构揭秘系列的第 1 篇。我们会逐层拆解这个为 DeepSeek 量身打造的终端编程 Agent 的设计内核。今天先聊最核心的：**Agent Loop**。

---

## 🎯 Nova 是什么

一个在你终端里干活的 AI 编程助手——读代码、跑命令、改文件、搜文档，把任务从头推到尾。但今天不聊功能，聊它的大脑——`agentLoop`。

---

## 🔄 Agent Loop：一场永不中断的对话

AI Agent 的本质是什么？是一个循环：

```
模型思考 → 要调工具？→ 执行工具 → 把结果喂回去 → 模型再思考 → ...
                                                              ↓
                                                          任务完成，结束
```

Nova 把这个循环实现为 `agentLoop` 函数，大约 300 行 TypeScript。但 300 行代码撑起一整个编程助手的调度核心，凭什么？

答案就一句话：**核心只管状态流转，所有行为都委托给 Hook**。

---

## 🪝 唯一的扩展点：HookRegistry

权限控制、上下文压缩、日志写入、UI 刷新——这些功能在大多数 Agent 框架里，要么硬编码在循环里，要么通过一堆零散的配置项拼凑。

Nova 的做法是：**所有这些，全部以 Hook 的形式挂在同一个注册表上，Loop 本体不耦合任何一个具体功能。**

用代码类比，就像 Express.js 的中间件——但你只能通过一个统一的 `.on()` 接口来注册，没有第二种方式。

这种约束带来一个巨大的好处：**看 Loop 源码，一眼就能读懂状态机逻辑；加新功能，永远不需要改 Loop。**

---

## 🚦 Hook 的两条轨道：一个能拦路，一个只能看

Nova 把 Hook 分成两种语义：

| 类型 | 能做什么 | 典型场景 |
|------|---------|---------|
| **Blocking（阻塞型）** | 改写请求、否决操作、注入消息 | 权限拒绝、触发压缩、插入提醒 |
| **Advisory（通知型）** | 纯观察，不能干预 | UI 更新、日志记录、统计上报 |

关键设计：**阻塞 Hook 有短路规则**——多个 Hook 排队执行，第一个返回结果的直接生效，后面的不跑。这意味着你可以链式组合多个权限策略，而不需要在一个大函数里写 if-else。

整个生命周期覆盖了 **16 个 Hook 点**：

```
用户输入 → pre_compact → pre_request → 模型调用 → post_request
         → post_assistant → pre_tool_use → 执行工具 → post_tool_use
         → post_user_message → pre_continue → 下一轮循环
```

---

## 📝 Append-Only：一个看似简单却极其关键的约束

Loop 有一个铁律：**消息历史只能追加，不能修改、不能删除、不能调换顺序**。

这不是代码洁癖，而是为 DeepSeek 的自动前缀缓存服务的。DeepSeek 会缓存请求的开头部分——只要前缀逐字节不变，后续请求就直接复用缓存，响应快到飞起、token 成本骤降。

Nova 整个消息管线为此做了三层保障：

1. **追加语义封装**：`appendMessage` 是唯一新增消息的入口，返回新数组，不碰旧数据
2. **发送前清洗**：消息携带的内部标记（比如"这条是系统注入的"）在发送给模型前会被 `toWireMessages` 剥离，保证 wire format 永远稳定
3. **压缩不删历史**：上下文太长需要压缩时，只是在末尾追加一个边界标记，旧消息原封不动留在磁盘上

实测缓存命中率**很高**，这在同类工具中非常罕见。

---

## 🛠️ 工具执行的分阶段处理

模型说要调 5 个工具——Nova 怎么处理？

**第一阶段：逐个过权限闸门。** 每个工具调用依次经过 `pre_tool_use` Hook，权限策略可以逐个拒绝（拒绝的工具会收到一个友好的错误结果，而不是悄无声息地消失）。

**第二阶段：并发执行。** 通过的调用按配置的并发数（默认 3）并行跑，结果通过 `post_tool_use` Hook 还能被改写——比如对输出脱敏或截断。

还有一个"防御底线"：**即使某个工具执行挂了、超时了、被用户取消了——Loop 保证每个 tool_use 都有配对的 tool_result**。这是模型 API 的硬要求，配对不完整下一轮请求会被直接拒绝。

---

## 🧠 max_tokens 截断不是终点

模型输出被长度限制腰斩了——大部分 Agent 的做法是直接报错，前功尽弃。

Nova 的处理很巧妙：

1. 先判断截断位置——如果截断发生在工具调用**之后**，说明模型已经做出了实质进展，继续执行工具即可
2. 如果截断发生在纯文本中间（没有工具调用），自动追加提示「从断点处继续，别重复」
3. 设置 `maxTokensContinuations` 上限（默认 3），防止模型永远写不完
4. **关键**：只要某一轮产生了工具调用，计数器立即重置——因为模型取得了实质进展

这意味着长任务不会因为一次截断就前功尽弃。

---

## 🏗️ 架构分层：谁都不能往上依赖

```
📦 CLI           ← 把所有能力串成终端应用
📦 Agent         ← 驱动 Turn 循环 + 持久化
📦 工具/上下文    ← 读写、搜索、LSP、记忆加载
📦 核心 (core)   ← Loop + Hook + 消息类型（零外部依赖！）
```

依赖方向严格单向：`core` 不知道什么是"工具"、什么是"终端"，它只输出 `MessageParam[]` 和接收 `ToolExecutor`——两个纯粹的类型。

这种分层让 `core` 可以独立测试、独立演进，甚至哪天想换掉整个工具系统，Loop 一行都不用改。
