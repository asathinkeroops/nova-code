# AI-native 架构标准

这是一份**通用**的 AI-native 架构自查标准，不绑定具体语言、框架、模型厂商或仓库结构。它用来回答一个问题：

> 我们是在把模型当作系统的运行时一等公民，还是只是在确定性系统旁边加了一个大模型接口？

标准按 **4 层、14 个维度** 组织，每个维度 0–5 分，总分 70。项目可以把它作为架构评审、季度自查或技术选型的检查表；自动化门禁由项目自行实现，本文只定义判据。

---

## 1. 什么算 AI-native

AI-native 不是「接入了 LLM」，而是：

> 把概率性的模型当作系统的主要控制面之一，围绕它的不确定性设计上下文、工具、状态、权限、人机协作、扩展组合、观测和评估；确定性代码负责提供能力、边界和保证。

区分：

- **AI-enabled**：原系统不变，在边缘加一个总结/分类/生成调用。
- **AI-native**：核心链路是「意图 → 规划 → 工具调用 → 环境反馈 → 修正」，模型在循环里。

**判断底线**：去掉模型，系统还剩下什么？如果只剩 CRUD，模型就是外挂；如果核心是模型循环、上下文、工具、状态和评估，才接近 AI-native。

还有两个容易被「模型/上下文/工具/状态」清单漏掉的维度：

- **人机协作**：AI-native 不是全自动，而是把人类的批准、中断、撤销、审计设计成系统的一部分。
- **扩展与组合**：新能力应该通过 port / hook / tool / plugin 组合进来，而不是每次改核心循环。

---

## 2. 四层模型

| 层                    | 关注点                                         | 包含维度                                                                          |
| --------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------- |
| **L1 运行时架构**     | 模型是否在核心链路里，系统是否为不确定性设计   | 1 控制流位置 · 2 上下文治理 · 3 工具/能力契约 · 4 状态与可回放 · 5 失败与不确定性 |
| **L2 工程保障**       | 能否安全地换模型、定位问题、验证改动、控制权限 | 6 模型抽象与路由 · 7 可观测性 · 8 评估体系 · 9 安全与治理                         |
| **L3 产品与交互**     | 人和模型如何协作，能力如何组合                 | 10 人机协作 · 11 扩展与组合                                                       |
| **L4 工程流程与组织** | 成本、性能、数据反馈和长期演进                 | 12 成本与性能 · 13 数据飞轮 · 14 工程流程                                         |

这四层的关系是：

- L1 决定「是不是 AI-native」；
- L2 决定「能不能安全地跑和改」；
- L3 决定「是不是一个可用的产品/系统」；
- L4 决定「能不能持续变好」。

## 3. 14 个维度

### L1 运行时架构

| #   | 维度           | 关键问题                                                     | 5 分信号                                                                                    | 低分信号                                                                     |
| --- | -------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 1   | 控制流位置     | 模型是在核心循环里，还是只在边缘调用一次？                   | 有 plan → act → observe → retry 的 loop；模型能选择工具、处理结果、修正计划；循环本身有测试 | 只有 `summarize()` / `classify()` 这类一次性调用，业务主流程仍是纯确定性代码 |
| 2   | 上下文治理     | 上下文是「拼字符串」，还是被当作有限资源管理？               | 有预算、检索、压缩、记忆、prompt cache；知道什么进上下文、什么留在磁盘；有回归测试          | 把所有历史直接塞进 prompt；上下文无限增长；没有压缩/预算                     |
| 3   | 工具/能力契约  | 模型能做的动作有没有清晰边界？                               | 工具带 schema、错误语义、幂等/并发约束；权限、审批、沙箱在工具层强制执行                    | 模型直接拼 shell/SQL/HTTP；没有权限模型；工具失败只返回一段自然语言          |
| 4   | 状态与可回放   | 一次运行能不能被完整重建？                                   | 会话、消息、工具结果、文件快照可持久化；有 transcript、检查点、replay；状态变更可审计       | 状态只在内存里；失败后只能靠日志猜；同一个输入无法复现                       |
| 5   | 失败与不确定性 | 模型超时、幻觉、上下文溢出、工具失败时，系统有没有确定行为？ | 超时/重试/降级/取消/上限/回滚都有定义；失败是结构化结果，不是静默吞掉                       | 只处理 happy path；模型一失败整个流程挂掉；没有 token/上下文上限             |

### L2 工程保障

| #   | 维度           | 关键问题                              | 5 分信号                                                                                                  | 低分信号                                                        |
| --- | -------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 6   | 模型抽象与路由 | 换模型/换 provider 要不要改业务代码？ | provider、模型档位、capability、成本/延迟路由有抽象；支持 fallback；换模型有测试                          | 模型 id、参数、SDK 调用散落在业务代码里；换模型要全局搜改       |
| 7   | 可观测性       | 一次回答为什么变成这样，能不能查？    | 按 turn/iteration/tool 记录 token、成本、缓存命中、工具结果、错误分类、耗时；有 correlation id 和聚合指标 | 只有最终输出；出了事无法定位是 prompt、检索、工具还是模型的问题 |
| 8   | 评估体系       | 改动是靠感觉，还是有回归？            | 离线 eval、replay harness、场景集、CI 回归；模型升级前先跑评估；失败样本可沉淀                            | 只靠人肉试 prompt；没有失败样本集；每次改完「看起来还行」       |
| 9   | 安全与治理     | 模型能不能越权？                      | 最小权限、沙箱、数据边界、prompt injection 防护、密钥隔离、审计、人工审批                                 | 模型可以任意读写/执行；把用户输入直接拼进系统提示；没有审计     |

### L3 产品与交互

| #   | 维度       | 关键问题                               | 5 分信号                                                                                    | 低分信号                                                                 |
| --- | ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 10  | 人机协作   | 高风险动作有没有确认、中断和退出机制？ | 流式输出、可打断、审批、plan/只读模式、撤销、可解释的中间状态；人类反馈能进入系统           | 只能等最终结果；模型做危险操作没有确认；出错只能重来                     |
| 11  | 扩展与组合 | 加一个能力要不要改核心 loop？          | port/hook/tool registry/plugin/MCP 等扩展点；依赖方向清晰；扩展继承权限边界；组合行为可观测 | 每加一个工具就改主流程；prompt、工具、业务逻辑互相耦合；扩展可以绕过权限 |

### L4 工程流程与组织

| #   | 维度       | 关键问题                             | 5 分信号                                                                          | 低分信号                                                 |
| --- | ---------- | ------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 12  | 成本与性能 | token、延迟、缓存是不是工程指标？    | 有预算、缓存、批处理、路由、上下文复用；成本/延迟可归因；有优化闭环               | 只关心「能不能答」，不关心每次调用多少钱、多慢           |
| 13  | 数据飞轮   | 真实使用能不能反哺系统？             | 失败样本 → eval → 工具/prompt/架构改进；记忆和反馈能沉淀；有版本归因              | 用户反馈只进工单；每次从零开始调；没有反馈到 eval 的路径 |
| 14  | 工程流程   | AI-facing 改动的质量门禁是否可重复？ | prompt/上下文/工具/模型变更纳入版本管理、测试、eval、CI；pre-commit/PR 门禁可执行 | 只靠人肉试 prompt；没有 CI；没有 eval；模型升级不做回归  |

## 4. 两个容易漏掉的维度

### 4.1 人机协作（维度 10）

- 高风险动作有确认/审批，且模型不能绕过。
- 中断、取消、失败后能恢复或回滚，不会留下半完成状态。
- 计划/只读模式真的限制动作，而不只是改变 system prompt。
- 中间状态可见：流式输出、工具调用、上下文占用、审批原因。
- 人工修正/反馈能进入系统，而不是只在 UI 上显示一次。
- 审批、权限模式切换、会话切换不会破坏状态和 prompt cache。
- 模型输出不被直接当作控制指令或权限依据。

### 4.2 扩展与组合（维度 11）

- 新能力通过 port / hook / tool registry / MCP / plugin 接入，而不是修改 core loop。
- 依赖方向清晰；新包不能反向依赖上层。
- 工具、子 agent、插件继承权限边界，不能通过组合扩权。
- 扩展点有契约、版本/兼容策略和测试，而不是靠命名约定。
- 扩展不破坏上下文、prompt cache、append-only 历史或权限边界。
- 新工具/子 agent 有 schema、description、prompt section 和权限故事。
- 组合行为可观测：能看出是哪个扩展、哪个工具、哪次调用产生了结果。

## 5. 0–5 分评分

每个维度 0–5 分：

- **0**：没有。
- **1**：有概念或临时实现，边界不清。
- **2**：有明确实现，但缺测试或自动化约束。
- **3**：有设计 + 测试，主要路径覆盖。
- **4**：有强制约束和自动化验证，换模型/换场景仍稳定。
- **5**：有度量与评估闭环，能持续发现并修复退化。

**注意**：5 分不是「功能多」，而是「可度量、可回归、可持续改进」。大多数项目会大量停在 3–4 分；这是正常的。

## 6. 评分表模板

| 层  | #   | 维度           | 分数 | 证据                         | 缺口 |
| --- | --- | -------------- | ---- | ---------------------------- | ---- |
| L1  | 1   | 控制流位置     | 0–5  | 代码/架构图/trace            |      |
| L1  | 2   | 上下文治理     | 0–5  | 预算/压缩/检索/prompt cache  |      |
| L1  | 3   | 工具/能力契约  | 0–5  | schema/权限/沙箱/错误语义    |      |
| L1  | 4   | 状态与可回放   | 0–5  | 持久化/transcript/checkpoint |      |
| L1  | 5   | 失败与不确定性 | 0–5  | 超时/重试/降级/上限          |      |
| L2  | 6   | 模型抽象与路由 | 0–5  | provider 抽象/fallback       |      |
| L2  | 7   | 可观测性       | 0–5  | 指标/trace/成本              |      |
| L2  | 8   | 评估体系       | 0–5  | eval/replay/CI 回归          |      |
| L2  | 9   | 安全与治理     | 0–5  | 权限/沙箱/审计               |      |
| L3  | 10  | 人机协作       | 0–5  | 审批/中断/撤销               |      |
| L3  | 11  | 扩展与组合     | 0–5  | port/hook/plugin             |      |
| L4  | 12  | 成本与性能     | 0–5  | 预算/缓存/路由               |      |
| L4  | 13  | 数据飞轮       | 0–5  | 反馈→eval→改进               |      |
| L4  | 14  | 工程流程       | 0–5  | CI/门禁/版本管理             |      |

14 个维度 × 5 分 = **70 分**：

- **0–23**：AI-enabled；
- **24–46**：AI-native 进行中；
- **47–70**：较成熟的 AI-native 架构。

分数只用于自查；不要为了分数把确定性边界交给模型。

## 7. 自查流程

1. **收集证据**：架构图、关键代码路径、一次真实运行的 trace、失败样本、现有 eval/测试。
2. **逐项打分**：每个维度必须有证据；没有证据按低分算。
3. **找最低三项**：它们通常就是最值得投入的改进点。
4. **制定行动**：把改进写成可验证的目标（例如「加 20 个 replay case」），而不是「加强 eval」。
5. **季度复评**：同一套证据标准，避免分数漂移。

### 提交/评审时的 10 个问题

1. 去掉模型，这个改动还剩下什么？模型是不是只在边缘？
2. 模型是否在核心循环里，能观察结果并修正？
3. 一次失败能否从 transcript/messages 完整回放？
4. 新工具是否有 schema、权限、沙箱、错误语义？
5. 上下文是否有预算、压缩、检索/缓存，而不是无限拼接？
6. 换模型/provider 是否需要改业务代码？
7. 模型超时、上下文溢出、工具失败时行为是否确定？
8. 有没有测试或 eval 覆盖这次 AI-facing 改动？
9. 高风险动作是否有人工批准、中断和撤销路径？
10. 新能力是否通过扩展点组合进来，而不是改核心 loop？

## 8. 常见反模式

- **AI wrapper**：产品看起来是聊天框，底层只是把用户输入转发给模型，没有工具、状态、权限。
- **RAG + prompt**：有检索和生成，但没有 agent loop、没有动作、没有环境反馈。
- **Agent demo**：有 loop 和工具，但状态不可回放、权限不设防、没有 eval，只在演示环境能跑。
- **Prompt spaghetti**：prompt 散落在业务代码里，没有版本、没有测试、没有 eval。
- **模型越权**：让模型直接决定金额、权限、事务、幂等，或者把模型输出当控制指令。
- **无限上下文**：不做压缩/检索/预算，只靠扩大窗口。
- **黑盒状态**：失败无法回放，出了问题只能靠日志猜。
- **只优化回答**：不优化失败路径、成本、延迟和可观测性。

---

## 9. 一句话原则

**让模型负责理解、规划、取舍和探索；让代码负责权限、事务、幂等、审计、重试、限额和边界；让人负责高风险决策和最终批准。**
